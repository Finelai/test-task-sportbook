# Задача 3. Линия, поток обновлений и гарантия цены

> **Для исполнителя:** выполнять этапы последовательно. Каждый этап затрагивает одну публичную HTTP- или внутреннюю gRPC-операцию и завершается ручной проверкой пользователем. Дождаться её результата до следующего этапа.

**Цель:** реализовать реальный сервис Линии с восемью матчами, обновляемыми котировками, персональными предложениями и их идемпотентным подтверждением.

**Архитектура:** отдельный Go-процесс владеет своей PostgreSQL. Два генератора передают данные в прикладной слой, который рассчитывает и сохраняет опубликованное состояние. HTTP и gRPC — адаптеры к прикладным сценариям; БД упорядочивает операции предложения и цены. Поток событий отправляет согласованный снимок и последующие обновления.

**Стек:** Go, net/http, grpc-go, PostgreSQL, pgx, sqlc, Goose, Docker Compose, OpenAPI и Swagger UI.

**Основание:** [задача 3 общего плана](2026-11-25-mini-sportsbook.md), [согласованное ТЗ](../specs/2026-11-25-mini-sportsbook-design.md), [опубликованные контракты](../../../contracts/openapi/v1.yaml), [line.proto](../../../contracts/proto/line/v1/line.proto).

## Общие условия

- Фиксированный серверный `PlayerID`; цены хранятся целыми сотыми и передаются в HTTP десятичными строками. Часы и seed генераторов управляемы в тестах; в обычном стенде два независимых источника обновляются каждые 5 секунд, устаревают через 15 секунд.
- Применять TDD: сначала добавить тесты этапа, увидеть их ожидаемое падение, затем реализовать код и запустить тесты повторно. Интеграционные тесты используют PostgreSQL через Testcontainers. Для исполнения нужны Docker и установленные зависимости проекта.
- До реализации соответствующей операции существующая заглушка может обслуживать её в отдельном профиле проверки; для ручной проверки текущая операция должна идти в реальный сервис Линии. Не направлять весь префикс `/api/v1/line` на заглушку или переключать будущие операции на неготовый сервис.
- Swagger доступен на `http://localhost:8080/docs/`. Для обычного HTTP использовать **Try it out → Execute**, для SSE — `curl -N`, для gRPC — `grpcurl`. Отдельный профиль ручной проверки открывает только тестовый gRPC-порт `localhost:9092`; в обычном Compose gRPC остаётся внутренним. Не запускать одновременно конкурирующий профиль `contract-check` на порту 8080.
- Не добавлять публичных маршрутов управления генераторами или временем. Граничные и конкурентные условия проверяются управляемыми тестами; ручные шаги подтверждают работу реального сервиса, но не заменяют эти тесты.
- `/healthz` и `/readyz` — внутренние служебные проверки, необходимые сервису: готовность требует выполненных миграций и доступной собственной БД. `/metrics` остаётся задачей 7. Не менять опубликованный контракт без явной необходимости и согласования.

## Файлы и границы

- `services/line/cmd/server/` — конфигурация, запуск сервиса и генераторов, завершение процесса.
- `services/line/internal/domain/pricing.go` — расчёт 1X2 и правила цены; `internal/app/line.go`, `offers.go` — сценарии, интерфейсы хранилища и часов.
- `services/line/internal/postgres/` и `services/line/{migrations,queries}/` — Goose, sqlc и транзакционное хранилище, принадлежащее только Линии.
- `services/line/internal/httpapi/` — HTTP и SSE; `services/line/internal/rpc/confirm_offer.go` — gRPC по существующему Protobuf.
- `services/line/integration/` и тесты рядом с кодом — проверки расчёта, конкурентности, транспорта и PostgreSQL.
- `compose.yaml`, `infra/nginx/default.conf`, Dockerfile сервиса — запуск и пооперационное переключение маршрутов; Swagger и остальные заглушки сохраняются доступными в ручном профиле.

## Этап 1. `GET /api/v1/line`: расчёт и снимок

**Зависимости:** существующий OpenAPI `LineSnapshot`. **Результат:** актуальный снимок из собственной БД и работающие генераторы.

- [ ] Написать `TestPrice`: для двух источников `[4,4,4]` сумма вероятностей до округления `1.05` с допуском `1e-9`, три результата `2.86`; изменение каждого источника влияет на результат. Отклонить нулевые, отрицательные, нечисловые и бесконечные коэффициенты, не публиковать частичный набор.
- [ ] Написать `TestStaleSourceClosesMarket`: источник свеж до границы 15 секунд, на границе рынок закрыт, восстановление обоих источников открывает его. Последний полный набор хранится до истечения свежести.
- [ ] Добавить интеграционный тест снимка: 8 матчей, у каждого `HOME`, `DRAW`, `AWAY`, строковые коэффициенты и монотонная версия; ошибка БД возвращает `503 unavailable`, готовность при недоступной БД не проходит. Запустить тесты и зафиксировать RED.
- [ ] Реализовать `Price(sources [2][3]float64) (Odds1X2, error)`: нормализовать обратные коэффициенты каждого источника до единицы, усреднить вероятности, умножить на `1.05`, обратить и округлить до сотых. Добавить генераторы, каталог, PostgreSQL, миграции, хранение версии и HTTP-адаптер.
- [ ] Настроить запуск, миграции, health/readiness и прокси только для `GET /api/v1/line` на реальную Линию. Добавить изолированный профиль ручной проверки, сохранив существующий контрактный стенд для других маршрутов.
- [ ] Запустить `go test ./services/line/...`, `go test -tags=integration ./services/line/... -count=1`, `docker compose --profile line-check config -q`; ожидание — код 0.

**Ручная проверка пользователем**

1. Запустить `docker compose --profile line-check up --build -d` и дождаться готовности Линии и PostgreSQL.
2. В Swagger открыть `GET /api/v1/line`, нажать **Try it out → Execute**. Ответ `200` содержит восемь матчей, названия команд, `open`, по три разных исхода и строковые коэффициенты.
3. Через 10–15 секунд повторить запрос: версия увеличилась и хотя бы одна опубликованная котировка изменилась. Если изменение случайно совпало после округления, повторить наблюдение; детерминированную проверку обоих источников выполняют тесты.

## Этап 2. `GET /api/v1/line/events`: SSE

**Зависимости:** снимок и версия этапа 1. **Результат:** подписка без пропуска между снимком и обновлениями.

- [ ] Добавить `TestSubscribeWithoutGap`: обновление до, во время и после подписки не теряется; после снимка версии идут по порядку. При переполнении ограниченной очереди соединение закрывается; новое подключение получает полный актуальный снимок. Зафиксировать RED.
- [ ] Реализовать согласованную подписку и снимок, последующие `match_updated`, инкремент версии при каждом опубликованном изменении. Отключить буферизацию и кэширование Nginx и переключить только этот маршрут на реальную Линию.
- [ ] Запустить `go test ./services/line/...`, `go test -race ./services/line/...` и интеграционные тесты с тегом `integration`; ожидание — код 0.

**Ручная проверка пользователем**

1. Пересобрать стенд `docker compose --profile line-check up --build -d`.
2. Выполнить `curl -iN --max-time 20 http://localhost:8080/api/v1/line/events`. Ожидаются `Content-Type: text/event-stream`, `event: snapshot` с восемью матчами, затем `event: match_updated` с матчем и большей версией. Завершение по тайм-ауту нормально.
3. Подключиться той же командой ещё раз: первым снова приходит полный `snapshot`. Непрерывность на границе подписки подтверждает автоматический тест.

## Этап 3. `POST /api/v1/line/offers`: выдача предложения

**Зависимости:** снимок этапа 1 и контракт `OfferRequest`/`Offer`. **Результат:** одно активное предложение на игрока, матч и исход.

- [ ] Добавить `TestOfferIssuedOnce`: повтор и параллельные запросы возвращают одинаковые `offerId` и `expiresAt`; истечение ровно через 60 секунд либо отклонение текущей цены более чем на `1.00` заменяет предложение без продления старого. Закрытый рынок — `409 market_closed`, невалидный запрос — `400 invalid_request`; неизвестный матч обработать в соответствии с опубликованным контрактом, не выдумывая неподдержанный статус.
- [ ] Добавить интеграционный тест гонки выдачи и изменения цены: блокировки дают один активный результат, согласованный с ценой. Запустить тесты и зафиксировать RED.
- [ ] Реализовать хранение предложения, уникальность активного предложения и транзакционную блокировку рынка и предложения; выдачу и замену упорядочить с будущим подтверждением. Переключить только маршрут предложения на реальный сервис.
- [ ] Запустить модульные и интеграционные тесты Линии и `make lint`; ожидание — код 0.

**Ручная проверка пользователем**

1. Пересобрать стенд `docker compose --profile line-check up --build -d`. В Swagger выполнить `GET /api/v1/line` и взять `matchId` открытого матча и один `outcome`.
2. Через **Try it out → Execute** отправить их в `POST /api/v1/line/offers`. Ответ `200` содержит `offerId`, выбранные матч и исход, строковый `odds` и UTC `expiresAt`.
3. Сразу повторить тот же запрос: `offerId` и `expiresAt` совпадают. Если цена успела выйти за допустимую разницу, получить новое предложение и повторить проверку сразу. Неизвестный исход должен дать `400 invalid_request`.

## Этап 4. `LineService.ConfirmOffer`: подтверждение цены

**Зависимости:** предложение этапа 3; `contracts/proto/line/v1/line.proto`. **Результат:** сохранённое по `bet_id` решение и одноразовое использование предложения.

- [ ] Добавить `TestOfferBoundaries`: `2.10 → 3.10` и `2.10 → 1.10` допустимы; `3.11` и `1.09` отклоняются. Проверить ровно `expiresAt`, закрытый рынок, другого игрока, неверный `expected_odds_hundredths` и неизвестное предложение; сверить причины с enum Protobuf.
- [ ] Добавить `TestConfirmOnce`: повтор тех же параметров и `bet_id` возвращает сохранённый результат даже после истечения, смены цены и перезапуска; иной `bet_id` не использует подтверждённое предложение. Изменение параметров для прежнего `bet_id` возвращает типизированный отказ или статус согласно контракту и не перезаписывает решение. Гонки подтверждений и выдачи не создают два успешных решения. Зафиксировать RED.
- [ ] Реализовать `ConfirmOffer(context.Context, *linev1.ConfirmOfferRequest) (*linev1.ConfirmOfferResponse, error)` в gRPC-адаптере и прикладной сценарий с сохранением решения и отпечатка запроса в одной транзакции под блокировками рынка и предложения. Временные ошибки возвращать статусом gRPC; решения — через `confirmed` или `rejected` из Protobuf.
- [ ] Включить реальный gRPC Линии в профиль ручной проверки на `localhost:9092`, не открывая порт в обычном Compose. Запустить `go test ./services/line/...`, `go test -race ./services/line/...`, `go test -tags=integration ./services/line/... -count=1`, `make lint` и `go test ./contracts/...`; ожидание — код 0.

**Ручная проверка пользователем**

1. Пересобрать стенд `docker compose --profile line-check up --build -d`. Получить новое предложение в Swagger, как в этапе 3. Записать `offerId` и `odds`, например `2.10` соответствует `210` сотым.
2. Выполнить команду ниже, подставив свои `offerId` и сотые коэффициента. `playerId` должен совпадать с фиксированным значением, указанным в документации конфигурации стенда:

   ```sh
   grpcurl -plaintext -import-path contracts/proto -proto line/v1/line.proto \
     -d '{"betId":"manual-bet-1","playerId":"player-1","offerId":"ВСТАВИТЬ_ID","expectedOddsHundredths":210}' \
     localhost:9092 line.v1.LineService/ConfirmOffer
   ```

3. До окончания срока действия ожидается `confirmed` с матчем, исходом и сотыми исходной цены. Повторить идентичную команду: ответ совпадает. Изменить только `betId` на `manual-bet-2`: ожидается `rejected` с причиной `OFFER_UNAVAILABLE`. Если срок истёк или цена вышла за допуск до первого вызова, получить новое предложение и повторить с новым `betId`.
4. Остановить стенд `docker compose --profile line-check down`. Проверить, что остановка не удаляет том PostgreSQL. Остальные границы, гонки и восстановление подтверждаются интеграционными тестами.
