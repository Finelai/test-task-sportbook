# Задача 2. Контракты и Swagger: план реализации

> **Для исполнителя:** применять `superpowers:executing-plans` при последовательной реализации. Каждый этап заканчивается ручной проверкой пользователем; переходить к следующему после её успешного результата.

**Цель:** последовательно опубликовать контракты семи публичных HTTP-операций и четырёх внутренних gRPC-операций, а также обеспечить доступ к OpenAPI через Swagger UI.

**Архитектура:** OpenAPI и Protobuf — источники контрактов. На время задачи отдельный локальный контрактный стенд возвращает фиксированные примеры; он не реализует бизнес-логику и не подменяет будущие сервисы. Nginx предоставляет документацию и маршрутизирует HTTP к стенду; gRPC-стенд доступен для проверки с хоста только в отдельном профиле Compose.

**Стек:** Go, OpenAPI 3, Protobuf, grpc-go, TypeScript, Nginx, Swagger UI, Docker Compose.

**Основание:** [Задача 2 общего плана](2026-11-25-mini-sportsbook.md), [согласованное ТЗ](../specs/2026-11-25-mini-sportsbook-design.md).

## Общие правила

- Один этап добавляет ровно одну HTTP- или gRPC-операцию. Общую инфраструктуру добавлять внутри первого этапа, которому она нужна. Не добавлять будущие операции заранее, включая заглушки маршрутов.
- Обычные HTTP-операции проверять кнопкой **Try it out → Execute** в Swagger UI. Для SSE использовать `curl -N`, так как Swagger UI не предназначен для наблюдения непрерывного потока; для gRPC — `grpcurl`, поскольку Swagger UI описывает HTTP API.
- Проверка каждого этапа — проверка публикации контракта и взаимодействия с фиксированным ответом стенда, а не доказательство работы реальных сервисов, БД, идемпотентности или бизнес-правил. Их реализация и проверка остаются в задачах 3–5.
- Все HTTP-маршруты имеют префикс `/api/v1`. Суммы и коэффициенты — десятичные строки, даты — UTC RFC 3339. Общая ошибка: обязательные `code` и `message`; применимые к операции коды взять из задачи 2.
- Контрактный стенд и его открытый gRPC-порт включать только профилем `contract-check`; не выдавать его за production-сервис. Не направлять на него обычный Compose без этого профиля.
- Версии генераторов, образов и инструментов закрепить. `make generate` повторяем; CI запускает генерацию и проверяет отсутствие изменений отслеживаемых сгенерированных файлов. По мере добавления операций расширять `contracts/contract_test.go`, запускать его и проверять конфигурацию Compose. Следовать TDD: сначала тест на добавляемую операцию, убедиться в RED, затем описать контракт и получить GREEN.
- Инструкции ниже рассчитаны на Docker Compose, `curl` и `grpcurl` на машине пользователя. Для gRPC использовать локальный `.proto`, поэтому серверная reflection не требуется. Примеры gRPC используют `localhost:9091`; HTTP и Swagger — `localhost:8080`. Зафиксировать эти порты в профиле проверки.
- Сгенерированные типы описывают контракт, а не подтверждают его реализацию. Не добавлять коммиты без отдельного решения пользователя.

## Карта файлов

- `contracts/openapi/v1.yaml` — публичные операции, общие схемы и примеры.
- `contracts/proto/line/v1/line.proto`, `contracts/proto/wallet/v1/wallet.proto` — внутренние операции и сообщения.
- `contracts/contract_test.go` — проверки опубликованных контрактов по мере их добавления.
- `contracts/generated/` и `apps/web/src/shared/api/generated/` — Go-код Protobuf и TypeScript-типы OpenAPI; точные команды и версии закрепить в `Makefile` и конфигурации генераторов.
- `tools/contract-check/` — изолированный сервер фиксированных примеров HTTP/SSE и gRPC; добавлять обработчики только текущего этапа.
- `infra/nginx/default.conf`, `compose.yaml` — документация, маршруты и профиль проверки; `.github/workflows/check.yml` — проверка воспроизводимости генерации.

## Этап 1. `GET /api/v1/line`

- [ ] Добавить тест наличия операции, `200`, JSON и обязательных полей `version`, `matches`, полей матча и трёх исходов. Запустить `go test ./contracts -run TestPublishedContracts -count=1` и зафиксировать RED.
- [ ] Описать операцию и схемы снимка, матча и котировки в OpenAPI. Исходы: `HOME`, `DRAW`, `AWAY`; `odds` — строка. Указать применимые общие ошибки.
- [ ] Настроить генерацию TypeScript, её проверку в CI, Nginx и локальный Swagger UI: `/docs/` и `/docs/openapi.yaml`. Создать профиль `contract-check` и сервер с фиксированным снимком одного матча, в котором три котировки; настроить проксирование этого маршрута. Один матч здесь — только пример контракта, рабочая линия из восьми матчей появится в задаче 3.
- [ ] Выполнить `make generate`, `go test ./contracts -run TestPublishedContracts -count=1`, `docker compose --profile contract-check config -q`; ожидание — код 0.

**Ручная проверка пользователем**

1. Запустить `docker compose --profile contract-check up --build -d`.
2. Открыть `http://localhost:8080/docs/`: интерфейс показывает `GET /api/v1/line`. Открыть `http://localhost:8080/docs/openapi.yaml`: загружается тот же контракт.
3. В Swagger раскрыть операцию, нажать **Try it out → Execute**: ответ `200` содержит `version`, `matches`, матч с `matchId`, названиями команд, `open` и тремя котировками; `odds` представлены строками.

- [ ] Описать SSE, начальный снимок и полный снимок при переподключении. Добавить фиксированные события стенда и отдельный маршрут Nginx без буферизации и кэширования.
- [ ] Перегенерировать типы и выполнить контрактный тест и `docker compose --profile contract-check config -q`.

**Ручная проверка пользователем**

1. Пересобрать стенд: `docker compose --profile contract-check up --build -d`.
2. Выполнить `curl -iN --max-time 5 http://localhost:8080/api/v1/line/events`. Ожидаются `Content-Type: text/event-stream`, сначала `event: snapshot`, затем `event: match_updated`; JSON каждого события соответствует описанию в Swagger. Завершение `curl` по тайм-ауту допустимо.
3. Подключиться повторно той же командой: первое событие снова `snapshot`. Это проверяет пример стенда; отсутствие пропусков в реальном потоке проверяется в задаче 3.

**Ручная проверка пользователем**
