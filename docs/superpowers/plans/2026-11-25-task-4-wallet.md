# Задача 4. Кошелёк и операции резерва

> **Для исполнителя:** выполнять этапы последовательно с `superpowers:executing-plans`. Каждый этап реализует одну HTTP- или gRPC-операцию и заканчивается ручной проверкой пользователем; перед следующим этапом дождаться результата проверки.

**Цель:** реализовать сервис Wallet с чтением баланса, идемпотентным пополнением и надёжным резервированием, списанием и освобождением условных денег.

**Архитектура:** отдельный Go-процесс владеет базой `wallet` и журналом операций. HTTP и gRPC используют общие прикладные сценарии и PostgreSQL-транзакции; запись кошелька блокируется при изменении остатков. Идемпотентные результаты, в том числе отказ в резерве, сохраняются вместе с операцией.

**Стек:** Go, net/http, grpc-go, PostgreSQL, pgx, sqlc, Goose, Docker Compose, Swagger UI.

**Основание:** [задача 4 общего плана](2026-11-25-mini-sportsbook.md), [согласованное ТЗ](../specs/2026-11-25-mini-sportsbook-design.md), [OpenAPI](../../../contracts/openapi/v1.yaml), [wallet.proto](../../../contracts/proto/wallet/v1/wallet.proto).

## Общие условия

- Один фиксированный серверный `PlayerID`; начальный остаток `available=0`, `reserved=0`. Деньги хранятся как `int64` в минимальных единицах, в HTTP передаются десятичными строками с максимум двумя дробными знаками. Не использовать `float` при разборе и расчётах.
- Только одна новая операция на этап. Реализованные операции предыдущих этапов можно использовать для подготовки и проверки данных. Публичные HTTP-проверки выполнять через Swagger **Try it out → Execute**, gRPC — через `grpcurl`.
- Применять TDD: сначала добавить тесты текущей операции и увидеть ожидаемый RED, затем реализовать и получить GREEN. Интеграционные тесты работают с PostgreSQL через Testcontainers. Гонки проверять параллельными вызовами и инвариантами в БД, а не только HTTP-ответами.
- В профиле `wallet-check` одновременно запускать реальную Line и реальный Wallet через общий Nginx и Swagger. Три маршрута Line направлять в Line, маршруты Wallet переключать по мере реализации, а маршруты ставок до задачи 5 оставлять на контрактной заглушке. Не использовать конфигурацию `nginx-line` без изменения: сейчас она направляет оба маршрута Wallet в `contract-check`. На каждом этапе явно проверить, что запрос попадает в реальный Wallet. Открыть gRPC Wallet на `127.0.0.1:9093` только в профиле ручной проверки; в обычном стенде порт остаётся внутренним. Другие профили с портом `8080` одновременно не запускать.
- Для воспроизводимых ручных проверок создать отдельный проект Compose `wallet-manual` с собственным томом PostgreSQL: `docker compose -p wallet-manual --profile wallet-check up --build -d`. Начать с нового проекта, не удалять существующие тома без согласования. Сохранять этот проект и его данные между этапами; команды ниже предполагают последовательное выполнение всех ручных шагов один раз. Для повторного прогона выбрать новый уникальный `-p` и ключи операций.
- HTTP использует `{code,message}` и действующие коды из OpenAPI. Временные ошибки gRPC передаются статусом, а бизнес-результаты — перечислениями из `wallet.proto`. Не менять контракт без отдельного согласования. `/healthz` и `/readyz` — внутренние служебные маршруты; готовность требует успешных миграций и доступности собственной БД. `/metrics` относится к задаче 7.
- Line не вызывает Wallet: по ТЗ оба сервиса вызываются сервисом Bets. Поэтому прямое подключение Wallet к Line не требуется; настоящая межсервисная интеграция Line и Wallet через Bets входит в задачу 5. Совместный стенд здесь проверяет маршрутизацию двух независимых сервисов и замену заглушек Wallet.
- До интеграции ставок вызывать gRPC вручную с фиксированным `playerId: player-1`; документировать то же значение в конфигурации стенда и HTTP-адаптере. Пользовательский HTTP не принимает `PlayerID`.

## Карта файлов

- `services/wallet/cmd/server/`, `services/wallet/Dockerfile` — конфигурация, миграции, запуск HTTP и gRPC, готовность и остановка.
- `services/wallet/internal/domain/wallet.go` — сумма в минимальных единицах и допустимые переходы; `internal/app/operations.go` — сценарии и интерфейс транзакционного хранилища.
- `services/wallet/migrations/`, `services/wallet/queries/`, `services/wallet/internal/postgres/`, `services/wallet/sqlc.yaml` — схема, SQL и адаптер PostgreSQL. Журнал, кошелёк, идемпотентные пополнения и решения по `BetID` принадлежат только этой БД.
- `services/wallet/internal/httpapi/wallet.go`, `services/wallet/internal/rpc/reserves.go` — транспортные адаптеры по существующим контрактам; `services/wallet/integration/` и тесты рядом с кодом — модульные и интеграционные проверки.
- `compose.yaml`, конфигурация отдельного Nginx профиля, `services/wallet/README.md` — воспроизводимый запуск, маршрутизация и ручная проверка.

## Риски для проверки

- Переполнение при разборе суммы и при увеличении общей суммы `available + reserved` не должно изменить баланс или журнал — этап 2.
- Одновременные резервы не должны потратить один остаток дважды; сохранённый отказ нельзя превратить в успех после пополнения — этап 3.
- Повтор с изменёнными параметрами не должен менять исходный результат или баланс — этапы 2–3.
- Потеря ответа и повтор после перезапуска не должны повторно списывать или освобождать средства — этапы 4–5.
- Конкурирующие Capture и Release должны дать один конечный переход и одну запись завершения — этап 5.

## Этап 1. `GET /api/v1/wallet`: чтение баланса

**Вход:** OpenAPI `WalletBalance`, роль и база `wallet` из текущего Compose. **Выход:** реальный кошелёк с нулевыми остатками и сохранением состояния в PostgreSQL.

- [ ] Добавить `TestInitialBalance`: для нового игрока ответ `200` содержит `{"available":"0.00","reserved":"0.00"}`, повторное чтение не добавляет запись журнала. Добавить интеграционный тест недоступности собственной БД: `503 unavailable`, `/readyz` не проходит.
- [ ] Запустить `go test ./services/wallet/...` и `go test -tags=integration ./services/wallet/... -count=1`; зафиксировать RED из-за отсутствующей реализации.
- [ ] Добавить схему кошелька и журнала, адаптер PostgreSQL и сценарий чтения; при первом обращении безопасно создать единственный кошелёк игрока. Внедрить отдельный процесс с миграциями, HTTP и служебными проверками.
- [ ] Настроить профиль `wallet-check` с реальными Line и Wallet, Swagger и прокси только маршрута `GET /api/v1/wallet` на реальный Wallet; `POST /api/v1/wallet/credits` пока остаётся заглушкой. Документировать профиль и фиксированный `player-1` в `services/wallet/README.md`.
- [ ] Повторить модульные и интеграционные тесты и выполнить `docker compose --profile wallet-check config -q`; ожидание — код 0.

**Ручная проверка пользователем**

1. Запустить новый отдельный стенд: `docker compose -p wallet-manual --profile wallet-check up --build -d`. Дождаться готовности Wallet.
2. Открыть `http://localhost:8080/docs/`, раскрыть `GET /api/v1/wallet`, нажать **Try it out → Execute**. Ожидается `200`, `available: "0.00"`, `reserved: "0.00"`.
3. Через Swagger выполнить `GET /api/v1/line`: ответ реальной Line содержит восемь матчей. Повторить чтение кошелька после `docker compose -p wallet-manual --profile wallet-check restart wallet`: остатки те же. Стенд сохранить для следующих этапов.

## Этап 2. `POST /api/v1/wallet/credits`: пополнение

**Вход:** баланс этапа 1, OpenAPI `CreditRequest` и `CreditResult`. **Выход:** атомарное зачисление и сохранённый результат по игроку и ключу запроса.

- [ ] Добавить `TestCreditIdempotent`: два запроса `10.00` с ключом `credit-1`, включая конкурентные, возвращают один `operationId` и дают одно зачисление; тот же ключ с `11.00` даёт `409 idempotency_conflict`, баланс и журнал не меняются. После перезапуска повтор возвращает сохранённый результат.
- [ ] Добавить `TestInvalidAmount`: `0`, `-1`, `1.001`, некорректная строка, переполнение `int64` и переполнение `available + reserved` возвращают `400 invalid_request` без изменения БД. Отсутствующий или пустой `Idempotency-Key` — `400`. Суммы `0.01` и максимальное допустимое значение проверить без потери точности.
- [ ] Запустить тесты этапа и зафиксировать RED. Реализовать точный разбор суммы, блокировку кошелька, увеличение доступного остатка, запись журнала и результата в одной транзакции; запретить переполнение суммарного остатка и сохранить отпечаток запроса.
- [ ] Переключить только `POST /api/v1/wallet/credits` на Wallet; запустить модульные и интеграционные тесты, проверить отсутствие изменений контрактов.

**Ручная проверка пользователем**

1. Пересобрать тот же стенд: `docker compose -p wallet-manual --profile wallet-check up --build -d`.
2. В Swagger выполнить `POST /api/v1/wallet/credits` с заголовком `Idempotency-Key: manual-credit-1` и телом `{"amount":"10.00"}`. Ожидается `201`, `available: "10.00"`, `reserved: "0.00"`; записать `operationId`.
3. Повторить запрос: тот же `operationId`, баланс остаётся `10.00`. С тем же ключом и `11.00` ожидается `409` с `idempotency_conflict`. С новым ключом и `1.001` ожидается `400`. Проверить `GET /api/v1/wallet`: `10.00` и `0.00`. Повторить `GET /api/v1/line`: доступны восемь матчей; перезапустить Wallet и убедиться, что баланс сохраняется. Это подтверждает работу реальных сервисов на одном стенде, а не сценарий ставки.

## Этап 3. `WalletService.Reserve`: резервирование

**Вход:** пополненный кошелёк, `ReserveRequest {bet_id, player_id, amount_minor}`. **Выход:** сохранённый результат `RESERVED`, `INSUFFICIENT_FUNDS` или `PARAMETER_CONFLICT`.

- [ ] Добавить `TestConcurrentReserve`: при `available=10.00` два параллельных `BetID` по `7.00` дают один `RESERVED` и один `INSUFFICIENT_FUNDS`, остатки `3.00` и `7.00`. После пополнения повтор отказавшего запроса возвращает прежний отказ; изменение суммы для любого существующего `BetID` даёт `PARAMETER_CONFLICT`.
- [ ] Добавить тест повторного `RESERVED` после перезапуска и невалидных идентификаторов, нулевой и отрицательной суммы: запросы не меняют баланс и журнал, ошибки ввода передаются статусом gRPC `InvalidArgument`. Идентичный `BetID` другого игрока не может изменить существующий резерв.
- [ ] Зафиксировать RED, затем реализовать блокировку кошелька, проверку отпечатка `bet_id`, `player_id`, `amount_minor`, сохранение успеха и отказа. При успехе атомарно перенести сумму из доступного в зарезервированный остаток и записать журнал; повтор возвращает сохранённый результат.
- [ ] Включить реальный gRPC Wallet на `127.0.0.1:9093` в ручном профиле, запустить модульные и интеграционные тесты и `go test -race ./services/wallet/...`.

**Ручная проверка пользователем**

1. Пересобрать стенд той же командой этапа 2. До вызова `GET /api/v1/wallet` показывает `10.00` и `0.00`.
2. Выполнить команду:

   ```sh
   grpcurl -plaintext -import-path contracts/proto -proto wallet/v1/wallet.proto \
     -d '{"betId":"manual-bet-1","playerId":"player-1","amountMinor":"300"}' \
     localhost:9093 wallet.v1.WalletService/Reserve
   ```

   Ожидается `RESERVED`. Повторить команду: снова `RESERVED`, а `GET /api/v1/wallet` показывает `available: "7.00"`, `reserved: "3.00"`.
3. Изменить в запросе только `amountMinor` на `400`: ожидается `PARAMETER_CONFLICT`; баланс не меняется. Данные `manual-bet-1` сохранить для этапа 4.

## Этап 4. `WalletService.Capture`: списание резерва

**Вход:** `ReserveKey {bet_id, player_id}` и созданный резерв. **Выход:** `CAPTURED`, `CAPTURE_PARAMETER_CONFLICT` или `ALREADY_RELEASED` по контракту.

- [ ] Добавить `TestCaptureIdempotent`: успешный Capture уменьшает `reserved` на сумму резерва без изменения `available`, создаёт одну запись завершения; повтор и повтор после перезапуска возвращают `CAPTURED` без повторного списания. Для другого игрока вернуть `CAPTURE_PARAMETER_CONFLICT`, отсутствующий резерв обработать документированным статусом gRPC без изменения остатков.
- [ ] Зафиксировать RED, затем реализовать атомарный переход `reserved → captured`, запись журнала и сохранение решения. Заблокировать кошелёк и запись резерва в едином порядке, который будет использовать Release.
- [ ] Запустить модульные и интеграционные тесты Wallet; ожидание — код 0.

**Ручная проверка пользователем**

1. Пересобрать стенд той же командой этапа 2, сохранив том и резерв `manual-bet-1`.
2. Выполнить:

   ```sh
   grpcurl -plaintext -import-path contracts/proto -proto wallet/v1/wallet.proto \
     -d '{"betId":"manual-bet-1","playerId":"player-1"}' \
     localhost:9093 wallet.v1.WalletService/Capture
   ```

   Ожидается `CAPTURED`. Повторить команду, затем проверить через Swagger `GET /api/v1/wallet`: `available: "7.00"`, `reserved: "0.00"`.

## Этап 5. `WalletService.Release`: освобождение резерва

**Вход:** `ReserveKey` и операции предыдущих этапов. **Выход:** `RELEASED`, `RELEASE_PARAMETER_CONFLICT` или `ALREADY_CAPTURED` по контракту.

- [ ] Добавить `TestReservationFinalState`: конкурентные Capture и Release одного резерва дают ровно один конечный переход и одну запись завершения; повтор победившего вызова возвращает прежний успех, противоположный вызов — `ALREADY_CAPTURED` или `ALREADY_RELEASED`. Остатки неотрицательны и соответствуют победившему переходу.
- [ ] Проверить `TestReleaseIdempotent`: Release возвращает сумму в `available`, уменьшает `reserved`, повтор и повтор после перезапуска не меняют остатки. Другой игрок получает `RELEASE_PARAMETER_CONFLICT`, отсутствующий резерв — документированный статус gRPC без изменения БД.
- [ ] Зафиксировать RED, затем реализовать атомарный переход `reserved → released` с тем же порядком блокировок и сохранением результата. Запустить `go test ./services/wallet/...`, `go test -race ./services/wallet/...`, `go test -tags=integration ./services/wallet/... -count=1`, `go test ./contracts/...` и `make lint`; ожидание — код 0.

**Ручная проверка пользователем**

1. Пересобрать стенд той же командой этапа 2. Создать новый резерв на `2.00` из оставшихся `7.00`:

   ```sh
   grpcurl -plaintext -import-path contracts/proto -proto wallet/v1/wallet.proto \
     -d '{"betId":"manual-bet-2","playerId":"player-1","amountMinor":"200"}' \
     localhost:9093 wallet.v1.WalletService/Reserve
   ```

   Ожидается `RESERVED`; Swagger показывает `available: "5.00"`, `reserved: "2.00"`.
2. Освободить резерв и повторить вызов:

   ```sh
   grpcurl -plaintext -import-path contracts/proto -proto wallet/v1/wallet.proto \
     -d '{"betId":"manual-bet-2","playerId":"player-1"}' \
     localhost:9093 wallet.v1.WalletService/Release
   ```

   Оба ответа — `RELEASED`; `GET /api/v1/wallet` показывает `available: "7.00"`, `reserved: "0.00"`.
3. Вызвать Release с `manual-bet-1`, списанным на этапе 4: ожидается `ALREADY_CAPTURED`. Вызвать Capture с `manual-bet-2`: ожидается `ALREADY_RELEASED`. Баланс остаётся прежним.
4. Остановить стенд `docker compose -p wallet-manual --profile wallet-check down`; том с данными сохраняется. Конкурентность и восстановление проверяют автоматические тесты.
