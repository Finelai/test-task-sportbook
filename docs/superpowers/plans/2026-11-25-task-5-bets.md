# Задача 5. Сервис ставок и восстановление обработки

> **Для исполнителя:** выполнять этапы последовательно. Каждый этап реализует одну HTTP-операцию и заканчивается ручной проверкой пользователем; переходить к следующему после её успешного результата. Для исполнения использовать `superpowers:executing-plans`, для изменений поведения — TDD, для итогового ревью — `superpowers:requesting-code-review`.

**Цель:** принимать ставки по предложениям Line, безопасно списывать средства через Wallet и восстанавливать обработку после временных ошибок и перезапусков.

**Архитектура:** Bets — отдельный процесс со своей PostgreSQL и ролью. POST сохраняет заявку и возвращает `202`, фоновый обработчик последовательно вызывает реальные gRPC `ConfirmOffer`, `Reserve`, `Capture`. Сохранённые этапы, аренда и повторяемые операции обеспечивают восстановление; GET показывает текущий статус.

**Стек:** Go, net/http, grpc-go, PostgreSQL, pgx, sqlc, Goose, Docker Compose, Swagger UI, Testcontainers.

**Основание:** [задача 5 общего плана](2026-11-25-mini-sportsbook.md), [согласованное ТЗ](../specs/2026-11-25-mini-sportsbook-design.md), [OpenAPI](../../../contracts/openapi/v1.yaml), [Line Protobuf](../../../contracts/proto/line/v1/line.proto), [Wallet Protobuf](../../../contracts/proto/wallet/v1/wallet.proto).

Не направлять этапные ветки в `master` и не создавать отдельные итоговые MR на этапы. Не перезаписывать чужую историю.
- После завершения обоих этапов выполнить итоговые проверки и ревью, опубликовать общую ветку и открыть **один MR/PR из `feat/bets-implementation` в `master`** со всеми изменениями задачи 5. Проверить CI; объединение с `master` не входит в эту задачу без отдельного указания.

## Общие условия

- Один серверный игрок `player-1`. HTTP принимает `amount` и `odds` десятичными строками, `Idempotency-Key` обязателен; суммы хранятся в целых минимальных единицах, коэффициенты — в целых сотых. Отклонять нулевые, отрицательные, лишние дробные знаки, переполнение и некорректный JSON до записи заявки.
- POST возвращает `202` и `{betId,status,amount,odds}`; GET — ту же схему с `200`, для `rejected` дополнительно обязателен `reason`. Причины строго из OpenAPI. Бизнес-отказы Line и недостаток средств — `rejected`; временная ошибка или потеря ответа оставляет `pending` и приводит к повтору, а не к отказу.
- Каждый вызов выполняется после сохранения соответствующего этапа. `accepted` записывается только после подтверждённого Capture; результат Line сохраняется с матчем, исходом и зафиксированной ценой до резервирования. При неподходящем предложении Wallet не вызывается.
- Аренда обработки — 15 секунд; gRPC deadline — 2 секунды; повторы с 1 секунды с экспоненциальным увеличением до 30 секунд. Значения конфигурируемы для тестов. Продление или завершение аренды условно по токену: устаревший worker не перезаписывает результат нового владельца.
- Существующие `wallet-check`, `line-check` и контрактный стенд могут занимать `8080`. Для проверки использовать отдельный Compose-проект `bets-manual` и профиль `bets-check`; одновременно не запускать профили, занимающие тот же порт. Не удалять чужие тома. На общем стенде Line, Wallet и Bets реальны; Nginx направляет все реализованные операции к ним, без заглушек для проверяемого сценария. Внутренние gRPC-порты не публиковать на хост в этом профиле.
- Внутренние `/healthz`, `/readyz`: готовность требует завершённых миграций и доступности собственной БД; `/metrics` относится к задаче 7. Контракты менять только при выявленной необходимости и отдельном согласовании.
- Для каждого этапа TDD: сначала тест и ожидаемый RED, затем реализация и GREEN. Интеграционные проверки используют реальную PostgreSQL и настоящие gRPC-серверы Line и Wallet, не импортируя внутренний код чужих сервисов; для потери ответа допустим тестовый прокси. Ручные HTTP-проверки — через Swagger **Try it out → Execute**.

## Риски для проверки

1. Потерянный ответ после ConfirmOffer, Reserve или Capture и перезапуск не должны повторить действие или потерять заявку — этап 1.
2. Одновременные POST с одинаковым ключом создают одну ставку; другой запрос с этим ключом даёт конфликт — этап 1.
3. Два worker с истёкшей арендой не могут перезаписать конечный результат или противоречить друг другу — этап 1.
4. Ставки на общий остаток не приводят к отрицательному балансу; недостаток средств и отказ Line не создают списание — этап 1.
5. Неизвестный идентификатор и отказанная ставка отображаются корректно, без раскрытия чужих данных — этап 2.

## Этап 1. `POST /api/v1/bets`: приём и обработка ставки

**Вход:** реальные Line и Wallet, OpenAPI `CreateBetRequest` и `Bet`. **Выход:** сохраняемая заявка и восстановимая обработка до конечного результата. До этапа 2 GET ставки остаётся заглушкой и не используется как доказательство работы Bets.

- [ ] Создать ветку `feat/bets-create` **от актуальной `feat/bets-implementation`**. Добавить тесты `TestBetIdempotency` и проверки HTTP: одинаковые параллельные POST с одним ключом и параметрами возвращают один `betId`; изменение `offerId`, `odds` или `amount` даёт `409 idempotency_conflict`; пустой ключ, некорректные суммы, коэффициенты и JSON дают `400 invalid_request` без записи.
- [ ] Добавить `TestRejectWithoutCharge`: все бизнес-отказы Line отображаются причинами из контракта, Wallet не вызывается при отказе Line; недостаток средств даёт `rejected/insufficient_funds` без Capture и списания. Конкурирующие ставки не списывают больше доступного остатка.
- [ ] Добавить `TestRecoverAfterConfirm`, `TestRecoverAfterReserve`, `TestRecoverAfterCapture`: использовать реальные PostgreSQL и gRPC Line/Wallet с прокси, который теряет ответ **после фиксации** каждого действия. Перезапустить Bets и повторить заявку: тот же `betId`, исходная цена, одна принятая ставка и одно списание. Проверить повтор после завершения аренды и одновременных workers с разными токенами.
- [ ] Запустить `go test ./services/bets/...` и `go test -tags=integration ./services/bets/... -count=1`, зафиксировать ожидаемый RED. Настроить детерминированное время/повторы тестов без дополнительных пользовательских маршрутов.
- [ ] Создать миграции Bets, таблицы заявок и этапов, уникальный ключ `(player_id, idempotency_key)`, отпечаток исходных параметров и транзакционную постановку. Добавить HTTP POST, точный разбор денежных значений, собственный `/readyz` и запуск сервиса.
- [ ] Реализовать worker `confirm_offer → reserve → capture` с сохранением выбранного этапа до вызова, сохранённым результатом Line, арендой и проверкой токена при записи. Подключить реальные gRPC-клиенты. Не использовать Release в обычном сценарии ставки; конфликт конечного состояния или параметров не маскировать как успешную ставку.
- [ ] Создать профиль `bets-check` с реальными тремя сервисами и их собственными БД, Swagger и Nginx. Направить только POST ставки в Bets, GET ставки оставить заглушкой до этапа 2; маршруты Line и Wallet направить в реальные сервисы. Описать подготовку и запуск в `services/bets/README.md`.
- [ ] Выполнить `go test ./services/bets/...`, `go test -race ./services/bets/...`, `go test -tags=integration ./services/bets/... -count=1` и `docker compose --profile bets-check config -q`; ожидание — код 0.

**Ручная проверка пользователем**

1. Запустить новый проект `docker compose -p bets-manual --profile bets-check up --build -d`, дождаться готовности сервисов и открыть `http://localhost:8080/docs/`. Проект сохранять между этапами.
2. Через Swagger пополнить Wallet на `10.00` с уникальным ключом, выполнить `GET /api/v1/line`, выбрать открытый матч и получить предложение через `POST /api/v1/line/offers`. Записать `offerId` и `odds`.
3. До истечения предложения отправить `POST /api/v1/bets` с уникальным `Idempotency-Key`, этим `offerId`, исходным `odds` и `amount: "3.00"`. Ожидается `202` с `betId` и статусом. Повторить **точно тот же** запрос с тем же ключом: `betId` совпадает; изменение суммы с прежним ключом даёт `409`.
4. Через несколько секунд проверить `GET /api/v1/wallet`: `available: "7.00"`, `reserved: "0.00"`; повтор POST не меняет баланс. При изменении цены или истечении срока до подтверждения получить новое предложение, использовать новый ключ и повторить; отказ не должен списать деньги. Зафиксировать `betId` и цену для этапа 2.
5. После проверки выполнить ревью и включить ветку этапа в `feat/bets-implementation`, затем начинать этап 2 от обновлённой общей ветки.

## Этап 2. `GET /api/v1/bets/{betId}`: чтение результата

**Вход:** сохранённая заявка этапа 1. **Выход:** актуальный статус конкретной ставки через HTTP.

- [ ] Создать `feat/bets-read` **от обновлённой `feat/bets-implementation`**. Добавить интеграционные тесты `TestGetBet`: для существующей заявки `200` и исходные `betId`, `amount`, `odds`, актуальный `pending`/`accepted` или `rejected` с `reason`; неизвестный ID — `404 not_found`, недоступная БД — `503 unavailable`. Проверить, что чужая заявка не выдаётся фиксированному игроку.
- [ ] Запустить тест и зафиксировать RED. Реализовать чтение из PostgreSQL с фильтром `player_id` и HTTP-адаптер по опубликованной схеме. Переключить только GET ставки с заглушки на Bets; убедиться, что остальные маршруты продолжают работать.
- [ ] Выполнить `go test ./services/bets/...`, `go test -race ./services/bets/...`, `go test -tags=integration ./services/bets/... -count=1`; ожидание — код 0.

**Ручная проверка пользователем**

1. Пересобрать тот же проект `docker compose -p bets-manual --profile bets-check up --build -d`. В Swagger открыть `GET /api/v1/bets/{betId}`, указать ID из этапа 1 и нажать **Execute**: ожидается `200`, `accepted`, сумма `3.00` и исходный коэффициент предложения.
2. Для неизвестного `betId` ожидать `404` с `code: not_found`. Для проверки отказа получить новое предложение и отправить ставку на сумму больше доступного остатка с новым ключом; затем запросить её по ID. Ожидается `rejected` и `reason: insufficient_funds`, баланс не изменился. Если предложение отклонено раньше проверки средств, повторить с новым предложением.
3. После проверки включить ветку этапа в `feat/bets-implementation`. Остановить стенд `docker compose -p bets-manual --profile bets-check down`; том с данными сохраняется.
